# ADR-0010：任务更新的乐观并发（version + 409）

- 状态：Proposed（已实现，待用户批准）
- 日期：2026-10-20
- 影响范围：`tasks` 表、任务更新 API、未来的同步协议
- 背景与问题：任务可能来自多个标签页或设备。产品明确禁止“无提示的整条 last-write-wins 覆盖”。1.2 需要最小可验证的冲突检测，为 1.5 的同步打基础。

## 备选方案及证据

| 方案 | 优点 | 缺点 |
|---|---|---|
| 整数 `version` + 409（选中） | 简单、显式、可测试；与离线和同步天然兼容 | 客户端需处理 409 并刷新/合并 |
| `If-Match` / ETag | 贴近 HTTP 语义 | 与 JSON PATCH 组合较繁琐，前端实现更重 |
| 字段级 last-write-wins | 无冲突提示 | 违反“不得静默覆盖”的要求 |

## 决策与理由

- `tasks.version` 从 1 开始，每次更新 +1；
- `PATCH /api/v1/tasks/:id` 接受可选 `version`：与当前值不一致时返回 `409 CONFLICT`，`details.currentVersion` 给出最新值；
- 前端在 409 时重新拉取该空间任务列表并提示用户，不做自动覆盖；
- 删除任务同样递增版本，避免“删除后又被旧客户端改回”。

## 安全/隐私/性能/成本影响

- 无额外存储成本；每次更新多写一列；
- 409 不泄露其他用户内容（仍先做空间权限校验）。

## 回退方案

若改用 CRDT/操作日志，可保留 `version` 作为调试字段，更新逻辑迁到同步层。
